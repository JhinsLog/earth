## D-1. 실시간 전파는 커밋된 뒤에만 나간다

**상황** — `FlareService.create`가 트랜잭션 **안에서** Redis로 발행하고 있었다. `IDENTITY` 전략이라
`save()` 시점에 INSERT가 나가 저장된 것처럼 보이지만, 커밋은 메서드가 끝난 뒤다. 그 사이에 예외가
나면 DB는 롤백되는데 pub/sub 메시지는 이미 나가 있다. 존재하지 않는 플레어가 모든 접속자 화면에 뜬다.
pub/sub에는 롤백이 없다.

| | A. `@TransactionalEventListener(AFTER_COMMIT)` | B. 트랜잭션을 저장까지로 좁히고 호출부에서 발행 | C. 그대로 둠 |
| --- | --- | --- | --- |
| 방식 | 서비스는 도메인 이벤트만 발행, 리스너가 커밋 후 Redis로 | 저장 메서드와 발행 코드를 분리 | — |
| 장점 | "커밋된 뒤에만 나간다"가 **구조로 강제**된다 | 발행 순서가 코드에 그대로 보인다 | 변경 없음 |
| 단점 | 흐름이 한 단계 간접적이라 발행 시점이 코드에서 바로 안 보인다 | 나중에 저장 메서드만 호출하면 발행이 **조용히 빠진다** | 드물게 터지고, 터지면 재현되지 않는다 |

**결정** — A. 플레어 등록과 채팅 두 경로 모두 `FlareChanged` / `ChatMessagePosted` 도메인 이벤트를
발행하고 `realtime/*Listener`가 `AFTER_COMMIT`에서 내보낸다.

**이유** — 실시간 전파 경로는 앞으로 늘어난다. 발행 순서를 매번 사람이 지키는 것보다 구조로
박아두는 편이 낫다. "실시간은 Redis pub/sub을 경유한다"는 기존 불변식과 같은 결이다.

**포기한 것** — 발행 시점의 가시성(주석으로 보완). 그리고 반대 방향, 즉 **커밋은 됐는데 발행이
실패하는 경우**(메시지 유실)는 여전히 남는다. 아웃박스 패턴이 정석이지만 현재 규모에서는 과하다.

## D-2. 지역 구독 알림은 트랜잭션 밖에서 만든다

**상황** — 플레어를 저장하는 트랜잭션 안에서 지역 구독자에게 보낼 알림까지 만들고 있었다.
알림 생성이 실패하면 사용자가 쓴 플레어까지 롤백된다.

**결정** — 알림은 커밋 후 리스너에서 만든다. 활성 트랜잭션이 없으므로 `notifySubscribers`의
`@Transactional`이 새 트랜잭션을 연다(전파 속성 변경 불필요).

**이유** — 알림은 부가 기능이다. 부가 기능의 실패가 핵심 데이터(사용자가 쓴 글)를 지우면 안 된다.
부수 효과로 플레어 저장 트랜잭션이 짧아져 D-3의 잠금을 쥐는 시간도 줄었다. 알림 생성은 구독 전체를
읽는 무거운 작업이다.

**포기한 것** — 플레어는 저장됐는데 알림만 빠지는 경우가 생길 수 있다.

## D-3. 시간당 등록 한도는 사용자 행 잠금으로 지킨다

**상황** — 등록 한도 검사가 "최근 1시간 등록 수를 센다 → 한도보다 적으면 저장한다"의 두 단계였다.
READ COMMITTED에서는 동시 요청이 모두 같은 카운트를 보고 통과한다. **한도 5에 동시 요청 15개를
보내면 11개가 저장됐다.** 도배를 막으려고 만든 제한이 정확히 도배 방식으로 뚫린다.

**결정** — 검사 전에 `userRepository.findByIdForUpdate()`(`PESSIMISTIC_WRITE`)로 작성자 행을 잠근다.

**이유**
- 같은 사용자의 요청만 줄을 서고 다른 사용자는 영향을 받지 않는다
- 잠금 대상이 사용자 행인 이유: 레벨별 한도를 도입하면 한도값도 같은 행에서 읽는다.
  한도와 카운트를 한 잠금 안에서 읽어야 판정이 일관된다
- 참고로 채팅 도배 제한은 Redis `INCR`이 원자적이라 이 문제가 없다.
  "확인 후 행동"이 아니라 "행동 후 확인" 구조이기 때문이다

**포기한 것** — 같은 사용자의 동시 등록은 직렬화된다(사람이 손으로 누르는 속도에서는 체감되지 않음).

**검증** — `FlareRateLimitConcurrencyTest`. 수정 전 15개 중 11개 저장, 수정 후 5개.

## D-4. 공감 수와 수명 연장은 플레어 행 잠금으로 지킨다

**상황** — `Flare.applyConfirmation()`이 공감 수 증가와 만료 시각 연장을 모두 "읽어서 계산하고 쓴다".
`UNIQUE(flare_id, user_id)`는 같은 사람의 중복만 막는다. **서로 다른 10명이 동시에 공감하자 공감 수가
1이었다.** 공감 기록은 10건이 남았으니 카운터만 어긋났다. 더 큰 문제는 **수명 연장도 함께 유실된다는
것**이다. 사람이 몰려 동시 공감이 겹치는, 하필 가장 중요한 플레어에서 "여러 명이 목격한 사건은 오래
남는다"는 전제가 틀어진다.

| | A. 플레어 행 비관적 잠금 | B. SQL 원자 증가 | C. `@Version` 낙관적 잠금 |
| --- | --- | --- | --- |
| 방식 | `findByIdForUpdate()` 후 엔티티 메서드로 갱신 | `SET confirm_count = confirm_count + 1` | 충돌 시 예외 |
| 장점 | 수명 계산 규칙이 **엔티티 안에** 그대로 남는다. D-3과 같은 패턴 | 잠금이 없어 빠르다 | 경합이 없을 때 비용이 없다 |
| 단점 | 같은 플레어의 공감이 직렬화된다 | 상한 계산 등 수명 규칙이 SQL로 새어 나가 도메인 로직이 쪼개진다 | 재시도 로직이 필요하고, 사용자에게 "다시 눌러주세요"를 보여주게 된다 |

**결정** — A. 공감 취소도 같은 이유로 잠근다.

**이유** — 코드베이스에 동시성 전략을 하나만 남긴다. 수명 규칙(생성 시각 기준 상한)을 엔티티에서 지킨다.

**포기한 것** — 인기 있는 플레어 하나에 공감이 몰리면 그 플레어의 요청은 줄을 선다.

**검증** — `FlareConfirmConcurrencyTest`. 잠금을 빼면 공감 수 1로 실패, 적용 후 통과(공감 수와 수명 모두 검증).

## D-5. 공감 취소는 자기가 늘려준 수명만큼 정확히 회수한다

**상황** — 공감 취소가 공감 기록을 삭제하면서 만료 시각은 그대로 두었다. 기록이 지워지니 중복 검사가
다시 통과하고, 재공감하면 연장이 또 붙는다. **공감과 취소를 반복하면 혼자서 상한(12시간)까지 밀어올릴
수 있었다.** 공감이 0인데 기본 수명을 넘겨 살아 있는 플레어도 생겼다.

처음에는 "되돌리면 취소로 남의 플레어를 죽일 수 있다"는 이유로 되돌리지 않았는데, 그 판단에서 반대
방향(무한 연장)이 검토되지 않았다.

**결정** — 공감할 때 실제로 늘어난 시간을 `flare_confirmations.granted_seconds`(V4)에 기록하고,
취소할 때 정확히 그만큼만 차감한다. 그 결과 만료 시각이 지났으면 즉시 소멸한다.

**이유**
- 자기가 준 만큼만 회수하므로 **공감이 없었던 상태로 돌아가는 것**이다. 원래보다 나쁘게 만들 수
  없어서 공격 수단이 되지 않는다
- 대칭이라 어뷰징이 구조적으로 막힌다. +5 −5 +5 … 의 순 기여는 최대 +5분
- 5분을 그냥 빼면 안 된다. 상한에 걸린 공감은 실제 기여가 5분보다 적어서, 준 것보다 많이 회수하게 된다
- "확인되지 않은 플레어는 스스로 소멸한다"가 정확히 지켜진다

**포기한 것** — 취소하는 순간 플레어가 사라질 수 있다. 최소 N분 보장 같은 완충은 두지 않는다.
그 N분이 반복으로 누적되면 같은 어뷰징이 다시 열린다.

**검증** — `FlareConfirmWithdrawTest` 2건(공감·취소 10회 반복 후 수명 원복, 유일한 공감 취소 시 소멸).

## D-6. 뷰포트 조회는 bbox + 정렬 + LIMIT으로 하고, 인덱스는 측정 후 정한다

**상황** — 측정 결과 처음 가설(위경도 복합 인덱스의 선두 컬럼 문제)은 중심 문제가 아니었다.
- 프론트가 범위(bbox) 조회를 한 번도 호출하지 않는다. 항상 전 세계 최신 500개를 받는다.
  플레어가 많아지면 **내 동네 플레어가 안 보인다**
- bbox 쿼리에 LIMIT이 없고, 날짜변경선을 넘는 화면에서 경도 조건이 깨진다
- 측정 조건: 별도 컨테이너(postgres 17, 메모리 512MB), 이력 100만 행(만료 97%) 합성 데이터

| 쿼리 | 보이는 플레어 2,000 | 보이는 플레어 200,000 |
| --- | --- | --- |
| 최신 500 (현재 사용 경로) | 2.3 ms | **86 ms** (20만 행 정렬) |
| bbox 한국 | 1.9 ms | **200 ms, 14만 행 반환** |

- `(latitude, longitude)` 인덱스는 38MB로 가장 크지만 이력 행까지 담고 있어 거의 쓰이지 않는다.
  실제 조회는 V2의 부분 인덱스(`status='ACTIVE'`, 80kB)가 받치고 있다
- `WHERE expires_at > now()` 부분 인덱스는 만들 수 없다. 인덱스 조건식은 IMMUTABLE이어야 하는데
  `now()`는 아니다. 시간이 흐르는 것은 행 변경이 아니어서 인덱스가 다시 평가되지 않는다.
  그래서 만료 스케줄러가 "시간 경과"를 "행 변경(`status`)"으로 바꿔 준다. 정확성은 조회 시점의
  `expires_at > now()`가 지키고, 스케줄러 지연은 성능에만 영향을 준다

**결정**
- bbox 정규화 + 날짜변경선 분기 + 정렬 + LIMIT으로 조회를 고친다. 프론트는 일정 줌 이상에서 bbox로 조회한다
- 인덱스는 **현재 그대로 두고 구현한 뒤**, 별도 측정 DB에서 인덱스 없음 / 현재 / 부분 / GiST(PostGIS)를 비교해 정한다

**이유** — 인덱스 설계는 실제 쿼리 형태가 정해진 뒤에 측정으로 고르는 게 맞다. 쿼리를 바꾸기 전에
인덱스를 먼저 만들면 엉뚱한 쿼리에 최적화하게 된다.

**포기한 것** — 구현 직후에는 대규모 데이터에서 최적이 아니다(측정 후 보완).

**1단계 결과 (2026-10-28)** — 같은 측정 조건(보이는 플레어 20만), 정렬은 최신순 하나만 둔다.

| 쿼리 | 이전 | 이후 |
| --- | --- | --- |
| bbox 한국 | 172 ms, 140,147행 반환, 정렬이 디스크로 넘침(3.3MB) | 107 ms, 500행, 메모리 top-N 정렬(136kB) |
| bbox 서울 | 15.7 ms | 15.4 ms (실행 계획 동일) |
| 날짜변경선(남태평양) | 동쪽 절반 누락 | 14 ms, 378행 (BitmapOr) |

남은 병목은 넓은 범위에서 해당 행을 전부 읽은 뒤 500개를 고른다는 점이다(한국 범위 14만 행).
최신순으로 걸어가다 500개에서 멈추려면 `created_at` 순서를 주는 인덱스가 필요하다. 이것이 2단계(인덱스 비교)의 주제다.

**2단계 결과: 인덱스 (2026-10-28, V6)** — 이력 100만 + 보이는 플레어 20만(한국 70%), PostGIS 이미지,
7회 중앙값. 후보는 모두 보이는 플레어만 담는 부분 인덱스(`WHERE status = 'ACTIVE'`)다.

| 쿼리 (해당 행) | 기존 | 최신순 | 위경도 | GiST | **최신순+위경도** |
| --- | --- | --- | --- | --- | --- |
| 전 세계 최신 500 (20만) | 45.2 ms | 1.6 | 45.3 | 45.8 | **0.9** |
| 한국 (14만) | 67.3 | 1.9 | 67.6 | 117.6 | **1.3** |
| 서울 (641) | 12.7 | 12.6 | 3.0 | 2.7 | **2.5** |
| 유럽 (95) | 8.8 | 8.9 | 0.9 | 1.1 | **0.8** |
| 날짜변경선 (496) | 15.2 | 15.3 | 3.1 | 2.7 | **2.8** |

- 범위의 밀도에 따라 맞는 길이 다르다. 빽빽하면 최신순으로 걷다 500개에서 멈추고, 성기면 위경도로
  해당 행만 읽는다. 두 인덱스를 함께 두면 플래너가 통계를 보고 고른다
- GiST는 한국 범위의 행 수를 잘못 추정해 14만 행을 다 읽었다. 점의 사각형 검색에서는 B-tree보다 나은 점이 없었다
- 기존 `(latitude, longitude)`(만료 이력까지 담아 36 MB)와 `status`(8 MB)는 지웠다

**범용 계획 문제** — 위 수치는 커스텀 계획이다. JDBC 드라이버는 같은 쿼리를 반복하면 서버 측 준비문으로
바꾸고, PostgreSQL은 몇 번 뒤 파라미터를 보지 않는 범용 계획으로 고정한다. 범용 계획은 범위를 아주 좁다고
가정해 위경도 인덱스에 고정된다. 기존 인덱스에서 한국 범위는 **436 ms**(이력 84만 행)였고, 두 인덱스를 둬도
80 ms였다. 1단계의 107 ms는 리터럴로 잰 값이라 실제 앱 경로를 대표하지 못했다.

앱 경로에서도 재현했다. 한 연결에서 범위 조회를 15회 하면 6회가 범용 계획이었다(`pg_prepared_statements`).
범위 조회 트랜잭션에서만 `plan_cache_mode = force_custom_plan`(`set_config(..., true)`, `SET LOCAL`과 같음)을
건다. 계획 비용 0.2~0.3 ms를 매번 내고 범위마다 맞는 인덱스를 얻는다. 연결 풀의 다른 쿼리에는 영향이 없다.

**포기한 것** — 범위 조회의 계획 재사용, 조회당 왕복 1회. 인덱스 두 개의 쓰기 비용(측정 데이터에서 합 10.6 MB).

## D-7. 외부 로그인 제공자가 주는 값의 길이를 신뢰하지 않는다

**상황** — 2026-10-14부터 구글 로그인 후 500이 났다. `insert into users`가
`value too long for type character varying(500)`로 실패했다. 구글이 준 프로필 사진 주소가
`profile_image_url VARCHAR(500)`을 넘었다. 같은 구조로 이름 50자 초과와 이름 누락(NOT NULL)도 500이었다.
기존 사용자도 로그인 때마다 같은 값으로 덮어쓰므로 주소가 길어지면 똑같이 막힌다.

| | A. 컬럼만 넓힘 | B. 컬럼 확장 + 저장 전 길이 방어 | C. 사진 주소를 저장하지 않음 |
| --- | --- | --- | --- |
| 재발 | 더 긴 값이 오면 재발 | 없음 | 없음 |
| 사진 | 표시 | 상한 이하면 표시 | 매번 제공자에게서 받아야 함 |
| 비용 | 마이그레이션 1개 | 마이그레이션 1개 + 코드 몇 줄 | 엔티티·DTO·프론트까지 변경 |

**결정** — B.
- V5: `profile_image_url`을 `VARCHAR(2048)`(URL 길이의 관례적 상한)로 넓힌다
- 사진 주소가 상한을 넘으면 **비운다.** 잘라내면 깨진 링크가 되기 때문이다. 주소 대신 길이만 경고 로그로 남긴다
- 닉네임은 50자를 넘으면 **코드 포인트 단위로** 자른다. PostgreSQL `VARCHAR(n)`은 문자 수로 세는데
  `String.length()`로 자르면 이모지 같은 서로게이트 쌍이 반으로 쪼개진다. 이름이 없으면 이메일 앞부분을 쓴다

**이유** — `picture`와 `name`은 제공자가 정하는 값이라 우리가 길이를 통제할 수 없다. 그리고
**부가 정보(사진) 때문에 핵심 경로(로그인)가 실패하면 안 된다.**

**포기한 것** — 상한을 넘는 사진 주소(사진 없이 이름만 표시).

**검증** — `GoogleUserUpsertTest` 5건(Testcontainers, 실제 PostgreSQL). 방어 로직과 V5를 뺀 상태에서는
5건 모두 운영과 같은 에러로 실패하고, 수정 후 전체 9건이 통과한다. 저장 로직을 `upsertGoogleUser`로
분리한 것도 이 때문이다. 원래 `loadUser`는 제공자 호출과 DB 저장이 섞여 있어 저장 부분만 검증할 수 없었다.

## D-8. 국가 판정은 Natural Earth 한국 관점 데이터를 기준으로 한다

**상황** — 비로그인 사용자는 접속 국가(Cloudflare 국가 코드) 안의 플레어만 상세 조회할 수 있게 한다.
플레어가 어느 나라에 속하는지 판정하려면 국경 데이터가 필요하다. Natural Earth(10m, v5.1.1)는
관점별 데이터를 제공하는데, **관점을 고르는 순간 그것이 곧 영토 정책이 된다.**

측정(PostGIS 3.5, `ST_Contains`):

| 지점 | 기본(사실상 지배) | 한국 관점 | 일본 관점 |
| --- | --- | --- | --- |
| 독도 폴리곤의 소유 | KOR | KOR | **JPN** |
| 독도 실제 좌표 | 어느 나라도 아님 | 어느 나라도 아님 | 어느 나라도 아님 |
| 마라도 | 어느 나라도 아님(데이터에 없음) | 같음 | 같음 |

독도 폴리곤은 점 5개짜리 사각형이고 실제 위치에서 약 0.5km 어긋나 있다. 그래서 순수 포함 판정만으로는
실제 독도 위의 플레어가 어느 나라에도 속하지 않는다.

**결정** — 국경은 Natural Earth **한국 관점(KOR)** 데이터를 쓴다. 독도는 대한민국으로 판정한다.

**이유** — 한국에서 운영하는 서비스로서 영토 판단을 일관되게 한다.

**포기한 것** — 국제적 중립성. 다른 관점을 가진 지역의 사용자에게는 판정이 다르게 보일 수 있다.

**국경 밖 판정** — 바다나 데이터에 없는 작은 섬 위의 플레어는 포함 판정에 걸리지 않는다.

| | A. 엄격 판정 | B. 영해(12해리) 안 최근접 국가 | C. 배타적경제수역(EEZ) 데이터 |
| --- | --- | --- | --- |
| 방식 | 육지 폴리곤 안이 아니면 국가 없음 | 포함 판정 실패 시 22,224m 안에서 가장 가까운 국가 | 해양 경계 데이터를 별도로 사용 |
| 섬·해안 | 대부분 빠짐 | 포함 | 포함 |
| 단점 | 해안·섬의 플레어가 판정되지 않음 | 양쪽 육지가 모두 가까운 해역은 실제 해상 경계가 아니라 거리로 갈림 | EEZ 자체에 분쟁 구역이 많고 데이터 라이선스 확인 필요 |

**결정** — B. 포함 판정을 먼저 하고, 실패하면 12해리 안의 최근접 국가로 판정한다. 둘 다 실패하면
국가 없음(공해)이다. 판정은 플레어를 **등록할 때 한 번** 하고 결과를 저장한다. 거리 계산이 포함 판정보다
무거워서 조회 때마다 하지 않는다.

측정(KOR 데이터):

| 지점 | 포함 판정 | 최종 판정 | 차순위 국가까지 |
| --- | --- | --- | --- |
| 독도 | 없음 | KOR (664m) | JPN 159km |
| 마라도 | 없음 | KOR (8.9km) | JPN 225km |
| 백령도·대청도·연평도 | KOR | KOR | PRK 13~26km |
| 연평도 남쪽 바다 3km | 없음 | KOR (1.8km) | PRK 15.6km |
| 대한해협 한가운데 | 없음 | 없음 | — |
| 진먼섬 | TWN | TWN | CHN 15km |
| 판문점 | **PRK** | PRK | KOR 1.3km |

**포기한 것** — 해상 경계와의 정확한 일치. 그리고 육상 국경의 정밀도: 10m 데이터는 단순화돼 있어
국경 근처가 약 1km 틀릴 수 있다(판문점 좌표가 PRK로 판정됨). 이 판정이 문제가 되면 보정 테이블로 덮어쓴다.

**구현 (2026-10-28)**

| 항목 | 결정 | 포기한 것 |
| --- | --- | --- |
| 데이터 적재 | Flyway `V6`에 0.01°(약 1km) 단순화 데이터(6.2MB, 250개 영역). 스키마와 함께 버전이 남고 테스트도 같은 데이터로 돈다 | 국경 부근 정밀도(육상 오차 약 1km → 최대 약 2km). 독도·마라도·서해 5도 판정은 원본과 같음을 확인 |
| 판정 위치 | DB 함수 `country_code_at` 한 곳. 등록 시점과 기존 데이터 보정이 같은 규칙을 쓴다 | 규칙이 Java가 아니라 SQL에 있다 |
| 판정 시점 | 플레어 등록 시 한 번, `flares.country_code`에 저장 | 국경 데이터를 바꾸면 기존 플레어는 다시 보정해야 한다 |
| 국가 코드 | `iso_a2_eh`(Cloudflare와 같은 alpha-2). `-99`는 NULL | 비르 타윌 등 일부 영역은 어느 나라에도 속하지 않음 |

판정 비용(PostGIS 3.5, 캐시 데운 상태): 국경 안 23~26ms, 국경 밖 근접 판정 48~60ms. 등록은 사용자당
시간당 5건이라 등록 시 한 번은 충분하지만, 조회 때마다 하기에는 무겁다.

**비로그인 공개 범위** — 로그인하면 전부. 비로그인이면 접속 국가와 같은 나라의 플레어만 상세이고, 나머지는
위치와 존재만(`restricted`). 접속 국가를 모르면(헤더 없음, Cloudflare의 `XX`, Tor의 `T1`) 아무 플레어의
상세도 주지 않는다. 판정은 서버가 한다. 클라이언트가 국가를 주장하게 두면 그대로 우회된다.
제한하는 것은 상세(작성자·내용·채팅·공감)뿐이고 지도 이동은 막지 않는다. 다른 나라 플레어가 어디에 얼마나
있는지는 보여주는 것이 로그인 유인이 되고, 위치는 막아야 할 정보가 아니라고 판단했다.
같은 이유로 첫 화면 라스에서 지도로 들어갈 때도 로그인을 묻지 않는다(2026-10-31). 예전에는 클릭하면 로그인
창이 떴지만, 제한은 이미 서버가 하므로 그 창은 막는 장치가 아니라 한 번 더 누르게 하는 화면이었다. 지금은
라스를 확대하거나 클릭하면 바로 들어가고, 로그인은 오른쪽 위 버튼으로만 한다.

**실시간 피드도 같은 기준** — REST만 막으면 같은 정보가 실시간으로 그대로 샌다. 실제로 이전에는 비로그인
연결이 전체 피드와 채팅 토픽을 구독할 수 있었다. 플레어 피드를 셋으로 나누고 구독 시점에 검사한다.

| 토픽 | 내용 | 구독 |
| --- | --- | --- |
| `/topic/flares` | 전체 | 로그인만 |
| `/topic/flares.public` | 위치와 존재만 | 누구나 |
| `/topic/flares.country.{CC}` | 그 나라 플레어의 전체 | 비로그인은 자기 접속 국가만 |

거부한 구독은 예외 대신 프레임을 버린다. 예외를 던지면 STOMP ERROR 프레임과 함께 연결이 끊겨 허용된
공개 피드까지 잃는다. 접속 국가는 STOMP 프레임에 없어서 WebSocket 핸드셰이크 때 세션에 남긴다.

검증: 실제 WebSocket 연결로 비로그인 사용자가 무엇을 받는지 확인하는 테스트에서, 구독 검사를 빼면
전체 피드로 작성자·내용까지 받는 것이 재현되고, 넣으면 공개 피드(위치만)와 자기 나라 피드만 받는다.

**신뢰 전제** — `CF-IPCountry`는 Cloudflare가 엣지에서 붙인다. 이 서버는 Cloudflare Tunnel 뒤에만 있어
클라이언트가 직접 닿을 수 없으므로 위조 경로가 없다. 직접 노출하면 이 헤더로 국가를 속일 수 있다.
VPN을 쓰면 다른 나라로 보이는 것은 IP 기반 판정의 본질적 한계로 받아들인다.

## D-9. 외부 데이터 플레어는 스냅샷 동기화로 맞추고, 중복은 DB 유니크 제약으로 막는다

**상황** — 서울시 실시간 돌발정보를 플레어로 만든다. 이 API는 "지금 진행 중인 돌발" 목록 전체를 매번 준다. 끝난 돌발은
알려 주지 않고 목록에서 빠질 뿐이다.

**① 목록에서 빠진 돌발**

| | A. 종료 예정 시각만 따름 | B. 빠지면 바로 종료 | C. 두 번 연속 빠지면 종료 |
| --- | --- | --- | --- |
| 장점 | 단순 | 현실과 가장 가까움 | 목록이 잠깐 덜 와도 깜빡이지 않음 |
| 단점 | 치운 사고가 예정 시각까지 남음 | 일부만 받고 비교하면 무더기로 꺼짐 | 종료가 최대 20분 늦음 |
| 포기하는 것 | 정확성 | 단순함 | 즉시성 |

**결정** — B. 단 **총 건수와 받은 행 수가 같을 때만** 비교한다. 목록이 깜빡이는 일이 운영에서 보이면 C로 바꾼다.

**② 같은 돌발이 플레어 두 개가 되지 않게**

"있으면 갱신, 없으면 생성"은 조회와 저장 사이에 틈이 있다. 스케줄러는 하나이고 같은 예약 작업은 겹치지 않지만,
백엔드를 여러 대로 늘리면 두 대가 같은 돌발을 동시에 처음 본다. 애플리케이션 판단만으로는 막을 수 없다.

**결정** — `(source, external_id)` 유니크 인덱스를 마지막 방어선으로 둔다. 늦게 INSERT한 쪽은 앞선 커밋을 기다렸다가
제약 위반으로 트랜잭션째 롤백된다. 전파는 커밋 후에만 나가므로(불변식 1) 실패한 쪽의 플레어가 화면에 뜨지도 않는다.
다음 주기에 그 돌발은 갱신 대상이 된다. 검증: 동기화 네 개를 동시에 출발시켜도 플레어는 하나(`ExternalFlareSyncTest`).

검토한 다른 방법: 분산 락(Redis)으로 수집 자체를 한 대만 돌게 하기 — 락이 풀린 틈이나 만료 시각 설정 실수에는 여전히
중복이 생길 수 있어, 어차피 DB 제약이 필요하다. `INSERT … ON CONFLICT DO NOTHING` — 중복은 막지만 JPA 엔티티와
"새로 생겼다" 전파를 따로 맞춰야 해서 지금 규모에서는 제약 위반 후 재시도가 단순하다.

**③ 작성자** — 시스템 계정(provider `SYSTEM`)을 두고, 플레어에 `origin`(USER/API)을 따로 적는다. 작성자를 nullable로
바꾸면 작성자를 가정한 응답·권한·채팅 코드를 모두 고쳐야 한다. 대신 로그인하지 않는 사용자 행이 생긴다.

**④ 수명** — 종료 예정 시각, 단 목록에 있는 동안은 최소 20분(수집 두 번). 예정이 지났는데 아직 처리 중인 사고가 만료
스케줄러에 꺼졌다 되살아나며 깜빡이지 않게 하려는 것이다. 공감으로 늘지 않는다 — 현실이 끝나면 플레어도 끝나야 한다.

**포기한 것** — 수집 실패가 길어지면 끝난 돌발도 유예(20분)나 예정 시각까지 남는다. 커밋은 됐는데 Redis 전파가 실패하면
그 변경은 다음 동기화까지 화면에 늦게 반영된다(아웃박스 미도입, 불변식 1과 같은 판단).

## D-10. 공공데이터 플레어 끄기는 화면에서만 거른다

**상황** — 설정 패널에 공공데이터(외부 API) 플레어를 끄는 스위치를 둔다. 비로그인 사용자가 접속 국가 밖의 플레어를 볼 때 서버는
위치와 존재만 담은 제한 응답을 주고, 이때 `origin`도 비운다. 그래서 그 경우에는 화면이 출처를 알 수 없다.

| | A안 | B안 | C안 |
| --- | --- | --- | --- |
| 방법 | 화면에서만 거름. 출처를 아는 플레어만 스위치를 따름 | A + 제한 응답에도 `origin`을 담음 | 서버 조회·실시간 전파에서 출처로 거름 |
| 장점 | 서버 변경 없음. 다시 켜도 재조회 없음 | 모든 사용자에게 같게 동작 | 꺼 두면 데이터가 오지 않음 |
| 단점 | 해외 비로그인 사용자에게는 꺼지지 않음 | 제한 응답이 정보를 하나 더 드러냄 | 켤 때마다 재조회, 구독 구조 변경 |
| 포기하는 것 | 일부 사용자에서의 일관성 | 제한 응답의 최소 정보 원칙 | 단순함 |

**결정** — A. 스위치는 화면 취향이고, 그 이유로 제한 응답의 원칙(위치와 존재만)을 풀지 않는다. 외부 데이터 플레어는
하루 수십 개라 받은 뒤 거르는 비용이 없다. 값은 브라우저(localStorage)에만 기억하고 기본은 켠다.

**포기한 것** — 제한 응답으로 받은 공공데이터 플레어는 스위치를 꺼도 남는다. 로그인하면 해소된다.

## D-11. 재연결되면 구독을 다시 걸고, 놓친 것은 REST로 채운다

**상황** — stompjs는 구독을 연결 하나에 묶어 두고, 연결이 끊기면 함께 버린다(7.3.0 `client.js`: 연결이 닫히면
`StompHandler`를 버리고 재연결 때 새로 만든다). 프론트는 구독을 한 번만 맺어서, 연결은 3초 뒤 다시 붙는데
채팅과 플레어 피드는 아무 표시 없이 멈췄다. 배포로 백엔드가 재시작될 때마다 모든 접속자에게 일어나는 일이다.
재연결은 처음 연결 때의 토큰을 다시 보내는데, 서버는 만료된 토큰의 CONNECT를 거절하지 않고 비로그인으로 받아
채팅방 구독이 막혔다.

수정 전 측정(로컬, 브라우저 두 개, 액세스 토큰 수명 90초로 줄임): A가 8초 끊김 / 토큰 만료 뒤 재연결 /
백엔드 재시작 — 세 경우 모두 A가 B의 메시지를 **받지 못함**, 화면 오류 표시 없음. 한 번은 열린 연결이 2개로 늘었다.

| | A안 | B안 | C안 |
| --- | --- | --- | --- |
| 방법 | 원하는 구독 목록을 연결 관리 쪽이 들고 있다가 연결될 때마다 다시 건다. 재연결 신호로 채팅 내역(최대 100건)·플레어 목록을 REST로 다시 받아 id로 합친다 | 재연결을 감지하면 화면 상태를 초기화하고 처음부터 다시 받는다 | A + 서버에 `afterId` 이후만 주는 API |
| 장점 | 서버 변경 없음. 끊긴 동안의 메시지도 채워짐 | 가장 단순 | 전송량 최소, 100건 상한과 무관 |
| 단점 | 재연결마다 최대 100건 재조회 | 끊길 때마다 열린 패널·입력 중인 글이 사라짐 | API·테스트 증가 |
| 포기하는 것 | 대화가 100건을 넘을 때 끊긴 동안의 앞부분 | 사용 경험 | 단순함 |

**결정** — A. 원인이 클라이언트의 연결 관리라 거기서 고친다. 플레어 수명 30분, 내역 상한 100건이라 재조회 비용이 작다.
함께 바꾼 것:
- 연결 직전(`beforeConnect`)에 토큰이 30초 안에 만료되면 먼저 갱신한다.
- 토큰 갱신이 서버에 닿지 못해 실패(네트워크 오류)하면 로그아웃하지 않는다. 처음 구현에서 재시작 중 갱신이
  실패해 접속자가 로그아웃되는 것을 재현 측정에서 발견했다. 그래도 만료된 토큰으로 연결되면 즉시 끊고 재시도한다.
- 재시도 중인 클라이언트를 버리고 새로 만들지 않는다(연결이 두 개가 되던 원인).
- 끊긴 동안의 전송은 기다리지 않고 바로 실패를 알린다.

수정 후 측정(같은 조건): 세 경우 모두 받음, 끊긴 동안 온 메시지도 내역 재조회로 채워짐, 열린 연결은 계속 1개 이하.

**포기한 것** — 대화가 100건을 넘으면 끊긴 동안의 앞부분은 채우지 못한다(내역 API가 최근 100건만 준다).
많아지면 C안을 더한다.

## D-12. 욕설·개인정보 검열은 서버의 규칙 기반 검사로 한다

**상황** — 채팅과 플레어에 욕설, 비방, 개인정보가 올라오면 그대로 전 세계에 실시간으로 퍼진다. 신고 기능은 아직 없다.

| | A안 | B안 | C안 |
| --- | --- | --- | --- |
| 방법 | 서버에서 금칙어 목록 + 개인정보 형식(휴대전화·주민등록·카드 번호, 이메일) 정규식으로 검사, 걸리면 저장 전 거절 | 외부 판별 API(LLM 등)에 글을 보내 판정 | 화면에서만 가림(저장은 함) |
| 장점 | 빠르고(마이크로초) 외부 의존 없음. 왜 막혔는지 설명 가능 | 비방·문맥까지 판단 | 구현 단순 |
| 단점 | 비방은 못 잡음. 새 우회 표현은 목록을 고쳐야 함 | 글마다 수백 ms~초 지연, 비용, 사용자 글이 외부로 나감 | API로 그대로 노출, 실시간 전파도 그대로 |
| 포기하는 것 | 문맥 판단 | 응답 속도·비용·외부 전송 최소화 | 실제 차단 |

**결정** — A. 채팅은 실시간이라 검사가 전송 경로에 지연을 더하면 안 되고, 사용자 글을 외부로 보내지 않는다.
금칙어 비교는 정규화한 글에 한다(소문자, 숫자·기호 제거, 한 글자씩 띄운 토막만 붙임). 공백을 전부 지우면
"다시 발표"가 "시발"에 걸리므로 지우지 않는다. 일상어와 겹치는 짧은 말("보지 마", "껌을 씹다", "시바견")은
목록에 넣지 않고, 그래도 겹치는 말("시발점")은 예외 목록으로 둔다. 통과해야 하는 일상 문장을 테스트로 고정했다
(`ContentModeratorTest`, 38개). 외부 데이터 동기화는 공공기관 원문을 그대로 전하므로 검사하지 않는다.

**포기한 것** — 비방·조롱처럼 문맥을 봐야 하는 글, "개 새끼"처럼 띄어 쓰면 일상어와 구별할 수 없는 우회.
신고 기능(보류)이 생기면 그쪽으로 보완한다.

## D-13. 차단 목록은 서버에 두고, 거르는 일은 화면이 한다

**상황** — 사용자가 특정 사람을 차단하면 그 사람의 플레어와 채팅이 보이지 않아야 한다. 플레어와 채팅은 REST(목록·내역)와
공유 토픽(`/topic/flares`, `/topic/chat.{id}`) 두 경로로 온다. 공유 토픽은 구독자 모두에게 같은 메시지를 보낸다.

| | A안 | B안 | C안 |
| --- | --- | --- | --- |
| 방법 | 목록은 서버(V10 `user_blocks`), REST·실시간 모두 화면에서 거름 | A + REST(목록·채팅 내역)는 서버 쿼리에서 거름 | 세션별 아웃바운드 인터셉터로 서버가 실시간 메시지도 사람마다 거름 |
| 장점 | 거르는 곳이 한 군데. 차단 즉시 기존 글도 사라짐. 공간 쿼리(D-6)를 건드리지 않음 | 차단된 글이 아예 오지 않음(REST) | 차단된 글이 브라우저까지 오지 않음 |
| 단점 | 차단된 글도 브라우저까지는 옴. 내역 100건에 차단된 사람 글이 섞이면 보이는 수가 줄어듦 | 거르는 곳이 두 군데. 측정해 둔 뷰포트 쿼리에 조건이 붙음 | 메시지마다 세션 수만큼 검사, 브로드캐스트 구조 변경 |
| 포기하는 것 | 전송량 최소화 | 단순함 | 브로드캐스트의 단순함과 성능 |

**결정** — A. 차단은 보는 사람의 취향이지 보안 경계가 아니다. 차단된 사람의 글은 다른 모든 사람에게 공개되어 있으므로
브라우저까지 오는 것이 정보 노출이 아니다. 차단은 `PUT`(몇 번 보내도 같은 결과)이고 `INSERT ... ON CONFLICT DO NOTHING`으로
넣어, 동시 요청 10개도 모두 성공하고 한 행만 남는다(`UserBlockServiceTest`). "있는지 보고 넣기"로 만들면 동시 요청 중 하나가
제약 위반(500)으로 실패한다.

**포기한 것** — 차단된 사람의 글도 네트워크로는 받는다. 대화가 길면 최근 100건 중 차단된 사람 몫만큼 덜 보인다.

## D-14. 모니터링은 Micrometer → Prometheus → Grafana로 홈서버 안에 두고, 서버째 죽는 것은 바깥에서 본다

**상황** — 수치도 알림도 없어, 장애는 직접 접속하거나 사용자 제보로만 알 수 있었다. 서버는 한 대(메모리 7.4GB)이고,
전원이 끊기면 하루 동안 켜지지 않는다. 오픈소스로만 고른다.

| | A안 | B안 | C안 |
| --- | --- | --- | --- |
| 방법 | 외부 업타임 체크만 | Micrometer(앱) + Prometheus·Grafana(컨테이너 2개) + 외부 업타임 체크 | B + postgres/redis/node exporter, Loki 로그 |
| 장점 | 가장 단순 | 느려짐·에러율·커넥션 풀·힙을 수치로 보고 전후 비교 가능 | DB·Redis·호스트 내부까지 보임 |
| 단점 | 살았는지만 앎 | 메모리 약 170MB(실측) 추가, 서버가 죽은 동안은 수치도 없음 | 컨테이너 3~5개 추가, node_exporter는 호스트 경로 마운트 필요 |
| 포기하는 것 | 원인 분석 | DB·Redis 서버 내부 지표, 로그 검색 | 단순함 |

**결정** — B. 앱 쪽 수치(HikariCP 대기, JVM 힙, 경로별 p95)만으로도 "느려졌다면 어디인가"의 첫 갈림길은 가를 수 있다.
수치(`/actuator/prometheus`)는 관리 포트 8081에만 열고 compose에서 publish하지 않는다. 8080은 Cloudflare Tunnel이 외부에
여는 포트라 요청 경로·응답 시간·JVM 상태가 그대로 공개되기 때문이다. 관리 포트를 나누면 `/actuator/health`도 8081로
옮겨 가는데, 헬스체크·`earth-ctl health`·외부 체크가 모두 8080의 그 경로를 본다. Spring의 `additional-path`는
한 단계 경로(`/healthz`)만 허용해(`'value' must contain only one segment`로 기동 실패) 기존 경로를 지킬 수 없었으므로,
`PublicHealthController`가 같은 `HealthEndpoint` 판정을 상태만 담아 8080에 다시 내보낸다(`ManagementPortTest`).
외부 체크는 별도 계정이 필요 없는 GitHub Actions 예약 실행(10분)으로 한다.

**포기한 것** — 서버가 죽어 있던 동안의 수치. 외부 체크의 즉시성(GitHub 예약 실행은 늦거나 건너뛸 수 있다).
DB·Redis 서버 내부 지표와 로그 검색은 필요해지면 exporter·Loki로 붙인다.

Grafana는 127.0.0.1에만 묶고, 바깥에서는 Cloudflare Tunnel(`earth-grafana.jhinslog.com`) 앞에 Cloudflare Access(지정한
메일 주소만 통과)를 두어 연다. Grafana 로그인만으로 인터넷에 열면 Grafana 취약점이 곧 서버 침입 경로가 되고, VPN(Tailscale 등)은
서버와 기기마다 설치가 필요해서다.
